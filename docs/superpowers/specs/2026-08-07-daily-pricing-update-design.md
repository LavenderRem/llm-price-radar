# 每日价格更新设计

## 目标

每天从已登记的服务商官方价格页检查价格变化，生成可审阅的 GitHub Pull Request。只有通过校验且由人工合并的价格才会进入生产站点。

## 范围

- 覆盖当前目录中的 OpenAI、Anthropic、Google、DeepSeek、阿里云百炼、智谱。
- 复用每个模型现有的官方 `sourceUrl`，不采集非官方聚合站。
- 保留现有价格目录、版本日期、官方链接和前端展示方式。
- 不在浏览器运行时抓取价格，不把未核验结果直接发布。

## 方案比较

1. 浏览器运行时直接请求官方页面：部署简单，但跨域、页面变动和结果不可追溯，不能保证稳定。
2. 每日脚本直接提交并发布：自动化最快，但页面解析错误会立即影响用户。
3. 每日脚本生成变更 PR：可追溯、可校验、可审核；多一步合并操作，但适合价格数据。

采用方案 3。

## 架构

```text
GitHub Actions（每日）
  -> scripts/sync-pricing.mjs
  -> 官方价格页抓取与服务商适配器
  -> 结构化候选数据 + 校验
  -> 变更报告
  -> GitHub PR
  -> 人工审核、合并
  -> Sites 重新部署
```

## 数据流与安全规则

1. 同步脚本读取 `site/src/data/catalog.js` 的模型、官方 URL 与当前价格版本。
2. 每个服务商适配器只提取其明确支持的字段；无法解析的字段为“未确认”，不能以猜测值替代。
3. 脚本写入候选目录与 Markdown 变更报告，报告列出旧值、新值、来源 URL、抓取时间和失败原因。
4. 校验器检查：金额为非负有限数、币种有效、价格日期有效、来源域名与服务商匹配、模型 ID 无重复。
5. 任一来源抓取或校验失败时，工作流失败并保留现有目录；不创建含不完整价格变更的 PR。
6. 工作流仅在候选数据与现有目录存在有效差异时创建或更新 PR；没有差异时成功结束。
7. PR 合并后由现有 Sites 发布流程部署。初期不自动合并、不自动覆盖生产价格。

## 组件

- `site/scripts/sync-pricing.mjs`：命令行入口、差异比较、报告生成、退出码。
- `site/scripts/pricing-sources/*.mjs`：每个服务商的抓取与解析适配器。
- `site/src/data/catalog.js`：仅保存已核验、已合并的价格版本。
- `site/tests/pricing-sync.test.mjs`：离线 fixture 测试解析器、校验器、失败保护和报告。
- `.github/workflows/daily-pricing-update.yml`：每天运行，支持手动触发，创建或更新 `automation/daily-pricing-update` 分支的 PR。

## 验证

- 单元测试覆盖每个适配器的官方页面 fixture、数字格式、阶梯价、缺失字段和来源失败。
- 同步脚本的 dry-run 不修改目录，只生成报告。
- CI 在更新前运行目录校验、全部前端测试和构建。
- GitHub Actions 使用最小权限：`contents: write`、`pull-requests: write`，不存储服务商密钥。

## 成功标准

- 每天定时任务可运行，也可手动触发。
- 价格变化会产生可审阅的 PR 和可读报告。
- 无变化不产生噪声 PR。
- 解析失败不会改动线上数据。
- 合并后数据日期、来源链接与前端展示一致。
